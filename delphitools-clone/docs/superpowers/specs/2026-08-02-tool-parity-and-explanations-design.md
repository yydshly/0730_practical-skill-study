# DelphiTools 剩余能力补齐与逐工具说明设计

日期：2026-08-02

## 目标

在现有 56 个可运行工具入口的基础上，尽可能补齐原站的重要能力，并在每个工具页面提供中文的能力说明、算法原理、处理流程、隐私边界和已知限制。

本阶段不再以“路由能打开”作为完成标准。完成度必须同时考虑输入、输出、格式范围、算法质量、交互流程、批量能力和导出能力。无法在浏览器中可靠实现的功能不得用简化算法冒充，必须明确说明原因、当前替代方案和后续实现条件。

## 当前状态

- 56/56 个独立工具入口已存在并可加载。
- 现有审计结论为：9 项基本对齐、27 项部分对齐、20 项明显缺口。
- 自动化测试目前为 384/384 通过，但这些测试只证明本地实现符合自身约定，不证明与原站逐项等价。
- 项目使用 React 18、TypeScript、Vite 和 Vitest，工具实现集中在 8 个工作区及其引擎、数据文件中。
- 现有运行时依赖主要是 `qrcode`、`bwip-js` 和 `pdf-lib`，不足以覆盖机器学习抠图、专业图片编解码、完整印前分析和词典式语音转写。

## 已确认的产品原则

1. 本地优先：文件和输入默认只在浏览器中处理，不上传服务器。
2. 允许为可靠能力增加浏览器端依赖、WASM、本地模型和合法可分发的数据集。
3. 不默认引入远程服务。确需服务端或第三方 API 时，先将该能力标为“当前无法本地可靠实现”，说明所需条件，不静默上传数据。
4. 尽最大可能实现；受浏览器能力、算法质量、数据许可、模型体积或性能限制的项目进入明确的未实现清单。
5. 中文优先：页面标题、控件、错误信息、能力说明和限制说明均使用易懂中文；必要的格式名、标准名和算法名保留英文原名。
6. 功能描述必须与真实实现一致。未实现的格式、算法或导出方式不得出现在无条件的能力宣传中。

## 实施路线选择

采用“分能力批次实施”，不采用一次性大爆炸式重写，也不只增加说明而停止补功能。

每个批次必须形成可独立验收的软件增量：先添加失败测试，再完成引擎或数据，再完成界面，最后更新该工具的说明与状态。批次之间共享统一的说明组件、状态模型、下载能力和测试约定。

## 逐工具说明系统

### 数据模型

在现有 `ToolDefinition` 之外增加独立的 `ToolExplanation` 数据。工具目录中的简短描述继续服务于搜索和卡片；详细说明服务于工具页面，避免把大量文字塞入路由注册表。

建议的数据结构：

```ts
export type ToolCapabilityStatus =
  | 'complete'
  | 'core-complete'
  | 'partial'
  | 'unavailable';

export type ToolExplanation = {
  toolId: ToolId;
  status: ToolCapabilityStatus;
  summary: string;
  capabilities: readonly string[];
  inputs: readonly string[];
  outputs: readonly string[];
  principle: readonly string[];
  workflow: readonly string[];
  privacy: string;
  limitations: readonly string[];
  unavailableReasons?: readonly string[];
  futureRequirements?: readonly string[];
};
```

状态含义：

- `complete`：审计范围内的原站核心能力、主要格式和主要流程均已对齐。
- `core-complete`：核心任务已可靠完成，仅缺次要快捷操作或展示细节。
- `partial`：可以完成主要任务，但仍缺重要格式、模式、交互、数据范围或算法质量。
- `unavailable`：当前实现不能可靠完成原站核心任务，或仅有不等价替代方案。

### 页面呈现

新增统一的 `ToolExplanationPanel`，放在每个工具工作区之后。默认显示简短状态和“这个工具如何工作”，其余内容使用可展开区域，避免压过主操作区。

每个页面必须包含：

1. 能做什么。
2. 支持的输入。
3. 可生成的输出。
4. 算法与实现原理。
5. 推荐操作流程。
6. 隐私与本地处理说明。
7. 当前限制。
8. 无法实现的原因和后续条件（仅在适用时显示）。

状态标签不使用模糊的“实验性”代替事实说明。处于 `partial` 或 `unavailable` 的工具必须列出具体缺口。

### 数据完整性

`toolExplanations` 必须覆盖全部 56 个 `ToolId`。注册表测试要验证：

- 不缺任何工具。
- 不存在重复说明。
- 状态值合法。
- `partial` 和 `unavailable` 至少有一条限制。
- `unavailable` 至少有一条无法实现原因或后续条件。
- 页面上的能力宣传不得包含已经标记为未实现的无条件承诺。

## 能力补齐批次

### 批次 0：说明基础设施与事实校准

- 建立详细说明数据模型、统一组件和样式。
- 为全部 56 个工具写入首版中文说明。
- 根据审计报告校准 `src/data/tools.ts` 中过度承诺的描述。
- 页面首先展示真实现状，即使某项能力尚未补齐。
- 增加说明覆盖率、状态约束和页面渲染测试。

这一批不改变工具算法，但会立即解决“英文能力看不懂”和“页面描述与实现不一致”。

### 批次 1：数据、表单和文本类低风险能力

优先处理不依赖大型模型、可用确定性算法测试的项目：

- 颜色转换：补 Decimal RGB、LAB、LCH、OKLAB、OKLCH 和逐格式复制。
- 色彩和谐：扩展方案类型、复制全部和 CSS Variables。
- Tailwind 色阶：补命名、生成模式、OKLCH、CSS Variables 和配置导出。
- 纸张尺寸：扩展 ISO A/B/C、RA/SRA、ANSI、建筑、日本、中国、瑞典、法国和 Imperial 数据，增加搜索、比较和 DPI 查询。
- 密码解码：补 Vigenère、Morse、Hex、Base64、手动模式和自动候选。
- Meta 标签：补 Site Name、Twitter Handle、Twitter Card 和社交预览。
- 正则测试：补常用预设和标志快捷控制。
- 文本处理台：补查找替换、提取和完整 Case/Lines/Clean Up 操作。
- 进制转换：补多进制同步显示、Bit Toggle 和位运算。
- 科学计算器：补 DEG/RAD、反三角、对数、阶乘、常数、Ans、EE、mod 和幂根。

### 批次 2：导出、批量和图像工作流

- 建立通用 ZIP 批量下载能力。
- 无缝轮播、图片分割、Favicon 和批量条码接入 ZIP。
- 占位图补 PNG/SVG 切换、尺寸预设和 URL 复制。
- 二维码补 URL、邮件、电话、SMS、WiFi、vCard、Geo 模板，增加尺寸、留白、PNG 和复制。
- 条形码补 Code 39、UPC-A、Micro QR（底层库可靠支持时）、颜色、留白、透明背景、PNG 和批量模式。
- 图片拼接补重排、缩放、对齐、individual/batch 模式。
- 图片转换补尺寸调整，并在实际编解码器支持的前提下扩展 GIF、BMP、TIFF、ICO；JXL 和 ICNS 单独验证浏览器编解码可行性后再承诺。
- 社交裁剪、水印和像素取色补可视化拖拽、放大镜、安全区和所见即所得交互。

### 批次 3：颜色生成、图像算法和专业质量

- 艺术品增强改回彩色噪声纹理叠加，不再用锐化和放大冒充原站能力。
- 调色板提取改为颜色空间聚类与主色合并，避免按精确像素频次产生照片噪点色。
- 调色板生成支持颜色锁定、增删、生成策略和 CSS/JSON/图片导出。
- 渐变支持多停靠点、角度、噪声、Linear/Corners/Mesh/Pigment 模式和 PNG 导出。
- 色盲模拟补整图模式和完整/部分色觉模式，使用有文献依据的颜色变换矩阵或模拟模型。
- 图片追踪增加路径简化、曲线拟合和质量选项；若浏览器端方案无法达到可接受质量，保留现有近似实现并明确标为部分实现。
- 背景移除优先评估浏览器端本地模型。只有在模型体积、许可证、内存和主流浏览器性能均可接受时替换现有 flood-fill；否则保留为不等价替代方案并标为当前无法完整实现。

### 批次 4：PDF、语言数据和 Substrata

- PDF 拼版补缩放模式、裁切/出血标记、预览和打印指南。
- Zine 拼版补 Accordion、8 张单页图片输入、纸张、DPI 和出血设置。
- PDF 预检先补可由浏览器可靠读取的页面框、字体引用/嵌入迹象、色彩空间和透明对象检查。ICC、总墨量等无法仅靠 `pdf-lib` 可靠判断的项目必须标明限制；若需要专业 PDF 解析 WASM，先评估体积和许可证。
- Shavian 转写需要可合法分发的发音词典、音素到 Shavian 的映射和未登录词回退规则。未满足数据许可和词典覆盖要求前，不把规则替换称为可靠转写。
- Substrata 分阶段补裁剪、选区、套索、魔棒、调色、画笔/铅笔、更多形状、缩放/适配、场景、工作区、FX、Looks 和 Arrange。每个工具组作为独立可测试增量，避免一次重写整个编辑器。

## 无法实现能力的处理

统一维护一份由详细说明数据生成的“未完整实现能力”汇总，避免手工报告与页面事实漂移。

每条未实现项包含：

- 工具名称和能力名称。
- 当前状态。
- 技术或许可原因。
- 当前可用替代方案。
- 实现所需条件，例如本地模型、WASM 编解码器、合法词典、服务端分析或更高性能预算。
- 是否涉及上传数据；若涉及，默认不开启。

构建产物中应提供可访问的总览页面或报告入口。审计 Markdown 可以作为快照，但页面数据是事实来源。

## 组件与代码边界

- `src/data/toolExplanations.ts`：56 个工具的详细说明与状态，纯数据，无 UI 逻辑。
- `src/components/ToolExplanationPanel.tsx`：统一呈现说明、状态和限制。
- `src/core/types.ts`：说明模型与状态类型。
- `src/components/ToolLayout.tsx`：在主工作区之后挂载统一说明组件。
- 各 `src/engines/*.ts`：保持纯算法和可测试转换，不混入 React 状态。
- 各 `src/tools/*Workspace.tsx`：只负责输入、状态、预览和导出流程。
- `src/data/*.ts`：纸张、调色板、Tailwind、Unicode、词典等静态数据。
- `tests/tool-explanations.test.tsx`：说明覆盖率、状态约束与页面可见性。
- 各现有引擎和工作区测试：按能力批次扩展，不建立一个无法定位问题的巨型总测试。

如果某个现有工作区文件因连续增加功能而失去清晰边界，应按工具或共享子能力拆分，但不做与本目标无关的全项目重构。

## 数据流与错误处理

1. 用户输入先做格式、大小和数量校验。
2. 确定性轻量算法直接在主线程运行；耗时图像、PDF 和模型任务使用 Worker。
3. 生成结果使用 Blob、Object URL 或文本结果在本地预览和下载。
4. 批量任务显示进度、成功数和失败项，不因单个文件失败丢弃全部结果。
5. 不支持的格式在用户选择前即禁用或解释，不接受后再静默降级。
6. Worker、WASM、模型或解码器失败时显示中文原因，保留原输入，并允许用户重试或改用已支持格式。
7. 所有临时 Object URL、Worker 和大内存缓冲区在组件卸载或新任务开始时释放。

## 测试策略

每项能力遵循测试驱动：

1. 为引擎写失败测试，覆盖正常输入、边界输入和错误输入。
2. 实现最小可靠算法，使测试通过。
3. 为工作区写交互测试，验证控件、状态、预览、下载和错误信息。
4. 运行受影响测试，再运行全量测试和生产构建。
5. 对 Canvas、文件上传、下载、Worker、WASM 和模型能力做真实浏览器冒烟测试。

算法等价性不能只用快照测试。颜色转换使用公开标准样例和容差；条码、二维码和 PDF 使用可被独立解析器读取的产物；图像算法使用小型确定性夹具和像素级断言；批量导出验证 ZIP 文件名、数量和内容类型。

## 验收标准

### 每个工具

- 页面能加载且没有控制台错误。
- 主任务可由用户完成，或页面明确标示当前无法可靠完成。
- 详细中文说明完整且与实现一致。
- 支持范围、限制和隐私边界准确。
- 新增能力具有引擎测试和必要的工作区交互测试。

### 每个批次

- 受影响测试通过。
- 全量测试通过。
- TypeScript 构建和 Vite 生产构建通过。
- 浏览器冒烟测试通过。
- 说明状态和未实现汇总同步更新。

### 项目最终完成

- 56 个工具均有统一中文说明。
- 审计中的 20 个明显缺口全部被实现，或有经过验证、可追溯的无法实现说明。
- 27 个部分对齐项逐条补齐，或保留具体差异说明。
- 重新执行原站与本地双端一致性审计。
- 最终报告明确区分“完整实现”“主要能力实现”“部分实现”“当前无法实现”，不再只报告入口数量。

## 非目标

- 不为了数字好看而伪造格式支持、算法质量或原站等价性。
- 不在用户不知情时把文件上传到第三方。
- 不一次性重写所有工作区或更换技术栈。
- 不追求与原站像素级视觉复制；本阶段优先保证能力、可靠性、中文可理解性和真实说明。
